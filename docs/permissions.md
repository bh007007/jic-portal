# 통합 관리 앱 권한 구조 (안, CL-025)

**상태: 설계안. 아직 코드·DB에 넣지 않았다.** 기획(원칙)과 DB 관리자(테이블·권한)가 승인하면 Change Log에 번호를 받아 단계별로 넣는다(`docs/collab.md` '공동 작업 방식').

- **근거**: CL-025(11/10) — 직원 화면은 하나의 통합 관리 앱, 권한은 **역할·캠퍼스·범위(보기·입력·승인)**로 정하고 **DB 권한 규칙으로 막는다**. **승인 권한은 메뉴 권한과 따로** 준다. Leo가 할 일: "관리자 앱을 통합 관리 앱의 기반으로 유지하고 메뉴 그룹별 권한 구조 설계".
- **출발점**: 11/9 승인된 역할별 권한표(`docs/roles.md`, 읽기·쓰기·캠퍼스)와 지금 코드의 메뉴(`docs/menus.md`). 이 안은 그 표를 새 틀(보기·입력·승인)로 옮긴 것이고, **누가 무엇을 하는지는 바꾸지 않는다.** 바뀌는 것은 '승인'을 따로 떼어 사람마다 줄 수 있게 하는 점이다.

## 1. 틀

| 요소 | 뜻 | 지금 | 안 |
| --- | --- | --- | --- |
| 역할 | 원칙 C5의 직원 역할: 선생님(T)·체커(C)·스케줄러(S)·매니저(M)·오피스(O)·관리자(A) | `user_roles.role`(직원은 `staff_users` + office·admin) | 그대로 |
| 캠퍼스 | 맡은 캠퍼스. 빈칸이면 모든 캠퍼스 | `user_roles.campus` | 그대로(11/10 상담 범위도 여기로 합침) |
| 범위 · 보기 | 메뉴 그룹의 화면을 연다 | 메뉴별로 코드·RLS가 따로 판단 | 메뉴 그룹 × 역할 표 하나로 |
| 범위 · 입력 | 그 메뉴 그룹의 기록을 만들고 고친다 | 함수 여럿(`is_staff`·`is_admin`·`is_lms_writer`·`can_schedule` …) | 같은 표에서 |
| 승인 | 다른 사람의 신청·후보를 확정하거나 반려한다 | 메뉴 권한에 섞여 있음(예: 결석 승인 = 매니저·오피스) | **사람마다 따로 주는 승인 권한**(아래 3장) |

DB에서는 세 가지 확인 함수로 모은다(이름은 안).
- `can_view(메뉴 그룹)`
- `can_input(메뉴 그룹, 캠퍼스)`
- `can_approve(승인 종류, 캠퍼스)`

정책(RLS)과 DB 함수가 이것만 부르게 하고, 지금 함수(`is_admin()` 등)는 옮기는 동안 이 함수를 부르는 얇은 함수로 남긴다. 화면은 같은 함수의 결과로 메뉴·입력 칸·승인 단추를 숨긴다. 숨기는 것은 편의일 뿐이고 막는 것은 DB다.

## 3. 승인 권한 (메뉴 권한과 따로)

승인은 '그 메뉴를 볼 수 있음'과 따로 사람마다 준다. 기본값은 역할에서 오되, 관리자가 사람별로 더하거나 뺄 수 있게 하는 안이다.

| 승인 종류 | 무엇을 | 지금 누가(DB) | 캠퍼스 범위 | 기본값 안 |
| --- | --- | --- | --- | --- |
| 결석 신청 승인·반려 | 학생 결석 신청(L4) | 매니저·오피스·관리자(`decide_absence_requests`) | 매니저는 캠퍼스 | 같음 |
| 무단결석 패널티 승인 | 시스템 후보(L5·I4) | 매니저(캠퍼스)·오피스·관리자(`penalties_manager_decide`) | 매니저는 캠퍼스 | 같음 |
| 통금 위반 패널티 승인 | 시스템 후보(I4·I7) | 오피스·관리자 | 모두 | 같음 |
| 외박·여행 신청 승인 | 학생 외박·여행 | 직원(`decide_overnight_permissions`) | 모두 | 오피스·관리자 |
| 생활 요청 처리 | 시설·청소 등(I12) | 직원(`handle_nonacademic_request`) | 모두 | 오피스·관리자 |
| 공항 이동 배차 확정 | 귀국 항공편 | 직원(`airport_rides`) | 모두 | 오피스·관리자 |
| 학교 여행 참가 제외 | 참가 명단 | 직원(`trip_remove_signup`) | 모두 | 오피스·관리자 |
| 변경 요청 처리 | 코스·기숙사 등 변경(1단계) | 직원(`change_requests`) | 모두 | 오피스·관리자 |
| 에이전시 가입 승인 | 지점 계정(P2, **P-12 결정 전**) | 직원(`approve_agency_request`) | - | 오피스·관리자 |
| 추천 규칙 승인본 지정 | 조건표 새 버전을 상담에 씀(센터장 승인 뒤) | 직원(`recommendation_rules`) | - | 관리자 |
| 출석 마감·사유 인정 | 하루 출석 확정 | 매니저·관리자(`is_lms_manager`) | 캠퍼스 | LMS 담당자 결정 |
| 역할·승인 권한 주기 | 사용자·권한 | 관리자(`is_admin`) | - | 관리자 |

지금은 '직원이면 모두'인 승인이 많다(외박·생활 요청·배차·여행·변경 요청·가입 승인·추천 규칙). 이 안대로 하면 처음으로 범위가 좁아지므로, 적용할 때 각 담당(인트라넷·회계 세션 포함)과 함께 권한 시험(`supabase/tests/*`)을 고친다.

## 4. 정할 것 (기획·DB 관리자)

1. **승인 권한을 사람별로 줄지, 역할 기본값만 둘지.** CL-025는 '따로 부여'다. 안은 역할 기본값 + 사람별 더하기·빼기.
2. **승인 권한을 누가 주는가.** 안: 관리자만('사용자·권한' 화면).
3. **센터장·DB 관리자를 역할로 둘지.** 조건표 승인(CL-023)은 지금 화면 밖에서 하고 관리자가 상태를 바꾼다.
4. **통금·근무자 설정의 메뉴 그룹**(기초관리 또는 학생 생활)과 오피스 입력 여부.
5. **메뉴 그룹 이름**(이 표의 '학생 생활'·'신청 처리'·'학사' 등). 지금 앱의 메뉴 이름을 그대로 썼다.
6. **표를 DB에 둘지(관리자가 화면에서 고침), 마이그레이션 코드로 둘지.** 안: 메뉴 그룹 × 역할 기본값은 표(`role_permissions`), 사람별 승인은 표(`approval_grants`), 둘 다 관리자만 고친다.

## 5. 넣는 순서 (승인 뒤)

1. 표와 확인 함수(`can_view`·`can_input`·`can_approve`)를 만든다. 지금 규칙과 같은 기본값을 넣어 **바뀌는 사람이 없게** 한다. 보안 규칙 시험(`security_lint.mjs`)과 역할 시험을 같이 고친다.
2. 관리자 앱 메뉴를 `can_view`로 숨긴다(지금은 '사용자·권한'만 숨김).
3. 승인 단추와 승인 DB 함수를 `can_approve`로 바꾼다. 처음으로 범위가 좁아지는 승인은 담당과 같이 한다.
4. '사용자·권한' 화면에 사람별 승인 권한 칸을 붙인다.
5. 인트라넷·강사 포털 화면을 관리자 앱 메뉴 그룹으로 옮기는 일(통합 관리 앱)은 이 권한 구조가 들어간 뒤, LMS 통합 결정과 함께 정한다.
