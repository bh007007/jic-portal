# 정한 원칙

업무 원칙의 원본이다(공동 작업 방식 11/10 안: 원칙이 DB와 코드보다 위). 원칙과 코드·DB가 부딪히면 코드를 고치기 전에 원칙을 먼저 바꿀지 기획과 논의한다(`docs/collab.md`).

- **지금 내용**: `JIC 통합 시스템 설계서_1109`의 '정한 원칙(입력처별)' 57개를 그대로 옮겼다(원칙 P4는 CL-024로 개정된 문구). 기획의 v1.0(2차 계획안 Day 7)을 받으면 이 파일을 바꾼다.
- **바꾸는 법**: 기획이 결정하고 `docs/change-log.md`에 CL 번호로 기록한 뒤 이 파일을 고친다. 이유와 보여 주는 곳까지 담긴 전체 표는 기획의 엑셀 '정한 원칙' 시트에 있다.
- **v1.2 합의 문서(Notion·Portal 역할 분리)와 다른 곳**은 차이 목록(P-·L-·N-)으로 관리하고, 결정되면 v1.2에 맞춰 고친다(`docs/agreements/`).
- **11/10 추가 결정**: CL-025(직원 화면은 하나의 통합 관리 앱, 권한은 역할·캠퍼스·범위), CL-026(PC 기준 먼저, 화면 폭 고정 없음). 아래 원칙 표에는 아직 들어가 있지 않다.

지금까지 정한 원칙 57개를 데이터를 쓰는 곳(입력처) 기준으로 나눴다. 원칙이 바뀌면 이 표와 엑셀의 '정한 원칙' 시트를 먼저 고치고, 다른 자료에 같은 내용으로 반영한다. 이유와 보여주는 곳까지 담긴 전체 표는 엑셀 '정한 원칙' 시트에 있다.
## 공통
| 번호 | 원칙 | 내용 | 상태 |
| --- | --- | --- | --- |
| C1 | DB는 하나, 회사 소유 | 모든 사이트(파트너 포털, 학생 포털, LMS, 인트라넷)는 하나의 공용 DB(Supabase, 싱가포르 지역)를 쓴다. 계정과 결제는 회사 명의로 한다. 지금 LMS와 파트너 포털 시제품은 DB가 연결되지 않았으므로 처음부터 공용 DB에 연결한다. | 대표 승인 필요 |
| C2 | 쓰기는 한 곳, 읽기는 필요한 곳 | 데이터마다 쓸 수 있는 시스템은 하나다. 다른 사이트는 권한 범위 안에서 같은 DB를 읽어 보여준다. 학생이 작성하고 직원이 처리하는 신청은 '작성'과 '처리 상태'의 쓰기 담당을 나눈다. | 확정 |
| C3 | 공통 학생 번호 | 업체 포털의 학생 번호를 모든 테이블의 기준 키로 쓴다. | 확정 |
| C4 | 캠퍼스 항목 | 모든 학생, 직원, 수업 기록에 캠퍼스(3곳)를 넣는다. 캠퍼스별 보기와 캠퍼스별 권한을 DB 하나로 처리한다. | 확정 |
| C5 | 역할과 권한 | 역할은 학생, 선생님, 체커, 스케줄러, 매니저, 오피스 직원, 관리자, 가드(외부 용역), 에이전시 지점이다. 직원은 등급과 부서로 권한을 정한다. 학생은 본인 기록만, 에이전시 지점은 자기 지점 학생만 보이도록 DB에서 권한 규칙을 건다. | 확정 |
| C6 | 로그인 | 우리가 만드는 사이트는 같은 로그인 체계를 써서, 직원은 한 번 로그인으로 LMS와 인트라넷을 오간다. 에이전시 계정을 직원·학생 계정과 같은 체계에 둘지는 정하지 않았다. | 미결정 (에이전시 계정) |
| C7 | 메신저는 만들지 않는다 | 개인 메신저, 채팅, 푸시 알림은 만들지 않는다. 알림이 필요하면 담당자 화면의 '확인할 일' 목록으로 보여준다. 학생 공지는 기존 메신저를 쓴다. | 확정 |
| C8 | 확인된 내용만 표시 | 확인되지 않은 가격, 공실, 학습 성과는 표시하지 않는다. 운영 전 기능과 캠퍼스는 '준비 중'으로 표시한다. | 확정 |
| C9 | 개발 순서 | 파트너 포털 → LMS → 학생 포털(단계적으로) → 인트라넷 순서로 만든다. 아직 개발되지 않은 기능은 지금 방식(수기)을 유지한다. | 확정 |
| C10 | 같은 설계를 공유한다 | 파트너 포털·학생 포털·인트라넷(사용자)과 LMS(필리핀 담당자) 모두 Claude로 개발한다. 공용 DB 설계표와 이 원칙 시트를 양쪽 Claude 프로젝트 지침에 똑같이 넣는다. | 확정 |
| C11 | 예산 | Supabase Pro로 시작하고 월 50달러 한도를 둔다. 3개월 사용 후 실제 청구액으로 다시 보고한다. 예상은 월 25~35달러. | 확정 (예산 승인 필요) |
| C12 | 보안 점검 | 실제 학생 정보를 넣기 전에 권한 규칙, 백업, 접근 기록을 점검한다. | 확정 |
| C13 | 큰 파일 관리 | 영상은 유튜브(일부 공개) 또는 드라이브 링크, 수업 자료는 회사 공유 드라이브 링크로 둔다. 녹음과 사진은 DB 저장소에 두되 정해진 규칙으로 지운다. | 확정 |

## 업체 포털
| 번호 | 원칙 | 내용 | 상태 |
| --- | --- | --- | --- |
| V1 | 기준 정보 | 학생 기본 정보, 입퇴학일, 기숙사와 공실, 등록, 수업 시간표 배정은 업체 포털이 기준이다. 업체 포털에는 더 이상 기능을 추가 개발하지 않는다. | 확정 |
| V2 | 신입생 엑셀 업로드 | 2주마다 업체 포털에서 내려받은 엑셀을 그대로 공용 DB에 올린다. 학생 번호가 같으면 새로 만들지 않고 덮어쓴다. 올릴 때 열 이름이 예상과 다르면 알려준다. | 확정 |
| V3 | 업로드 담당과 중간 추가 | 누가 업로드할지, 2주 사이에 급히 들어온 학생을 어떻게 추가할지(한 명씩 추가하는 화면 등)는 정하지 않았다. | 미결정 |
| V4 | 학생 계정 자동 생성 | 업로드할 때 학생 포털 계정이 학생 번호와 생년월일로 자동으로 만들어진다. 첫 로그인 때 비밀번호를 바꾸도록 요구한다. | 확정 |
| V5 | API로 교체 | 업체 포털 API가 가능해지면 엑셀 업로드를 자동 연결로 바꾼다. | 2차 |
| V6 | 시간표 배정 이전 | 시간표 배정을 업체 포털에서 자체 시스템으로 옮기는 것은 개발 범위가 커서 2차 과제로 둔다. | 2차 |

## LMS
| 번호 | 원칙 | 내용 | 상태 |
| --- | --- | --- | --- |
| L1 | 학업 정보의 입력처 | 출석, 시험 결과, 리포트(그로스, 스피킹, IELTS), Daily Recall, 녹음, 수업 변경 처리, 결석 승인은 LMS에서 입력한다. LMS는 선생님, 체커, 스케줄러, 매니저(열람과 결석 승인), 관리자가 쓴다. | 확정 |
| L2 | 시험 결과 구조 | 시험 기록은 하나의 구조로 저장하고 '시험 종류'로 구분한다(IELTS 밴드, TOEIC, ESL 레벨, 스피킹 평가). 화면은 코스별 성적표(주차별 상세)와 CEFR 공통 성장선 두 층으로 보여준다. 코스를 바꾸면 성장선에 변경 시점을 표시하고, CEFR 값은 'JIC 기준 추정 레벨'로 표기한다. | 확정 |
| L3 | CEFR 대응과 시험 주기 | ESL 내부 레벨과 CEFR의 대응 기준, 코스별 시험 주기(몇 주마다)는 정하지 않았다. | 미결정 |
| L4 | 결석 승인 | 학생 포털의 결석 신청을 매니저가 LMS에서 승인 또는 거부한다. 승인되지 않은 여행을 위한 결석 신청은 거부한다. 승인되면 출석에 인정 결석(병결, 공결 등)으로 남는다. 출석 현황에서 커서를 올리면 사유가 보이고, 사유별 합계가 나온다. | 확정 |
| L5 | 무단결석 목록 | 신청하지 않았거나 거부된 상태의 결석은 무단결석이다. LMS는 무단결석 목록을 보여주고, 매니저는 이를 보고 인트라넷에서 패널티를 승인한다. 패널티 점수는 JIC 내부 규정을 기본값으로 쓴다. | 확정 |
| L6 | 수업 변경 | LMS가 후보 선생님 2~3명을 추천하고 스케줄러가 확정한다. 반을 옮겨도 이전 기록은 지우지 않고 '언제부터 바뀜'으로 남긴다. 업체 포털 시간표는 스케줄러가 직접 고친다. | 확정 |
| L7 | 선생님 화면은 휴대폰 기준 | 수업 중 기록(출석, Daily Recall, 간단한 점수)은 휴대폰으로 몇 번의 터치로 끝나게 만든다. 긴 리포트는 태블릿이나 랩탑을 쓴다. | 확정 |
| L8 | 수업 자료실 | LMS에 수업 자료 목차(코스 → 교재 → 단원 → 자료 종류)를 만들고 파일은 회사 공유 드라이브의 구글 링크로 연결한다. 학생에게 공개할지는 정하지 않았다. | 확정 (학생 공개는 미결정) |
| L9 | 녹음 보관 | 녹음은 리포트 PDF만 보관하고, 녹음 파일은 졸업 후 정해진 기간이 지나면 자동으로 지운다(기간 미결정). 사례로 남길 녹음은 마케팅 사용에 동의한 학생만 선생님이 표시해 보관한다. | 확정 (보관 기간 미결정) |
| L10 | 스피킹 코스 리포트 사이트 | 현재 스피킹 코스 리포트 사이트는 LMS와 같은 공용 DB로 연결한다. 연결 방식은 LMS 담당자와 정한다. | 미결정 (방식) |

## 인트라넷
| 번호 | 원칙 | 내용 | 상태 |
| --- | --- | --- | --- |
| I1 | 학생 생활 정보의 입력처 | 패널티, 상담 기록, 외출·귀가, 통금·무단결석 승인, 사진, 졸업 후 사진 처리는 인트라넷에서 입력한다. 입력하는 매니저는 학생 생활 담당 매니저다. | 확정 (인트라넷 개발 후 적용) |
| I2 | Student File | 매니저가 학생 한 명을 관리하는 화면이다. 상담 기록, 패널티, 외출·귀가, 사진, 동의 현황을 관리하고, 출석률과 최근 시험 같은 학업 요약은 같은 DB에서 읽어 보여준다. 상세는 LMS에서 본다. | 확정 (인트라넷 개발 후 적용) |
| I3 | 패널티 점수제 | 위반 종류별 점수표를 두고, 위반이 승인될 때마다 점수가 합계에 더해진다. 합계가 기준점을 넘으면 경고 단계가 오르고, 담당 매니저와 관리자의 '확인할 일'에 뜬다. 위반별 점수, 단계별 기준점, 점수 소멸 시점은 정하지 않았다(출석은 내부 규정을 기본값). | 확정 (점수표 미결정) |
| I4 | 패널티는 승인된 건만 | 통금 위반과 무단결석은 시스템이 후보로 보여주고, 매니저(통금은 오피스)가 확인해 승인한 건만 점수가 된다. 자동 판정만으로는 패널티를 주지 않는다. | 확정 |
| I5 | 상담 기록 | 상담 기록은 내부 자료로 학생과 에이전시에게 보이지 않는다. 작성 폼에는 상담 내용, 아카데믹/논아카데믹 구분, 학생 피드백 약속(기한, 내용), 후속 조치 대상(스케줄러, 선생님)을 둔다. 상위 담당자는 기한이 지난 약속과 매니저별 상담 건수로 매니저를 관리한다. 담당 매니저와 상위 담당자만 보고, 열람 기록이 남는다. | 확정 |
| I6 | 외출·귀가는 카드키 QR | RFID는 장비 부담으로 도입하지 않는다. 학생은 외출 때 개인 카드키를 가드에게 맡기고 귀가 때 돌려받는다. 가드는 카드키의 QR을 태블릿 카메라로 찍고, 시스템이 시각과 학생 사진을 보여준다. 입실 때 오피스가 라벨(이름, 학생 번호, QR)을 출력해 붙이고, 방 번호는 넣지 않는다. 퇴실 때 라벨을 뗀다. | 확정 (인트라넷 개발 후 적용) |
| I7 | 외박 허용과 통금 확인 | 여행 신청이 승인되면 그 기간은 외박 허용 명단에 자동으로 오른다. 통금 시각에 외출 중이면서 외박 허용이 아닌 학생이 '확인 필요'에 뜨고, 오피스가 승인한 건만 통금 위반이 된다. | 확정 (개발 전 수기) |
| I8 | 가드 계정 | 가드는 외부 용역이며 외출·귀가 화면만 쓰는 별도 아이디를 받는다. 근무자별 아이디로 할지, 경비실 공용 아이디에 근무자 이름을 고르게 할지는 정하지 않았다. | 미결정 (방식) |
| I9 | 카드키 미반납 외출 | 카드키를 맡기지 않고 외출한 경우의 처리 규칙은 정하지 않았다. | 미결정 |
| I10 | 내부 공지와 권한 | 인트라넷 공지는 직원용 내부 공지만 다룬다. 공지 범위, 메뉴 권한, 결재선은 직원 등급과 부서로 정한다. | 확정 |
| I11 | 자료실과 양식 | 양식은 온라인 양식과 파일 원본을 같은 이름으로 함께 둔다. 공지 포스터는 게시 기간, 언어별 버전, 인쇄용·화면용 파일을 함께 올린다. 노션 마케팅 자료는 내부용이며 파트너 포털과 연결하지 않는다. | 확정 |
| I12 | 논아카데믹 신청 처리 | 여행, 시설 수리, 청소, 룸클리닝 미싱, 밴, 액티비티, 이벤트, 시티투어 신청은 오피스 직원이 처리한다. 신청 담당은 사람이 아니라 신청 종류에 연결한다. 개발 전까지는 지금처럼 수기로 받는다. | 확정 (개발 전 수기) |
| I13 | 졸업 후 사진 | 사진은 졸업 2주 후 담당 매니저가 저장 또는 삭제를 결정한다. 결정하지 않으면 자동으로 지우지 않고 다시 알린다. | 확정 |

| P1 | 역할과 단계 | 에이전시가 학생과 같은 화면을 보며 상담하는 도구다. 1차는 상담, 캠퍼스·코스, 견적·공실 연결, 자료실, 공지·프로모션, 방문 신청으로 학생 정보 없이 운영한다. My Students는 2차. | 확정 |

| P3 | 학생 개인정보 미저장 | 상담 중인 학생의 이름, 이메일, 답변을 저장하지 않는다. 학습계획서는 에이전시가 PDF로 받아 학생 동의 후 자기 메일에 첨부하거나 프린트한다. JIC는 지점별 다운로드 수만 집계한다. | 확정 |

Challenger ESL·IELTS는 스파르타/세미 스파르타 옵션이 있고 IELTS Guarantee는 스파르타만 운영한다. 수업 수로 나뉘는 코스(TEP 8·9·10교시, Speaking STARTER·PRO·MASTER 1:1 4·5·6개, 1:1 맞춤 과정 5·6교시)는 코스를 확정한 뒤 단계와 가격을 함께 보여주고 직접 고른다.
