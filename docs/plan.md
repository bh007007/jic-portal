# JIC 포털 자체 구축 기획안

> 원본(다이어그램 포함, 최신본): [Claude 문서](https://claude.ai/artifact/9JTCwocjZJFqPjdDjvZEg2). 이 파일은 2026-11-07 내보내기 사본이다.

## 개요

JIC 포털은 지금 쓰는 업체 포털(jicportal.com)의 데이터 구조를 회사 소유 Supabase DB로 옮겨 뼈대로 삼고, 그 위에 학생 포털·파트너 포털·인트라넷·LMS를 얹는 자체 통합 시스템이다. 코드는 GitHub, 화면 호스팅과 보안은 Cloudflare, DB·로그인·파일은 Supabase가 맡는다.

- **목적**: 업체 포털에 묶인 기준 데이터(학생, 입퇴학, 기숙사·공실, 등록, 시간표)를 회사가 직접 소유하고, 기능을 직접 추가·삭제할 수 있게 한다.
- **범위**: 업체 포털을 대체할 JIC 포털 관리자 화면, 학생 포털, 파트너 포털, 인트라넷. LMS는 필리핀 담당자가 같은 DB에 연결한다.
- **기존 설계와의 관계**: 11월 6일자 공용 DB 설계표(40개 테이블)와 정한 원칙을 그대로 따르고, 업체 포털에서 가져올 테이블을 '기준 정보' 그룹으로 더한다.
- **바뀌는 점**: 지금 원칙 V1은 업체 포털을 기준으로 두고 2주마다 엑셀을 올린다. 이 기획은 병행 운영 기간에만 그 방식을 쓰고, 모듈별로 쓰기 담당을 JIC 포털로 넘긴다.

설계는 이미 많이 나와 있었고, 비어 있던 업체 포털 내부 구조는 11월 7일 관리자 화면 분석으로 채웠다. 새 체제의 테이블 40개, 역할 9개, 원칙 61개가 정리돼 있고, 업체 포털에서는 테이블 약 50개를 확인했다.

## 기존 포털(jicportal.com) 분석

업체 포털은 메뉴 15개 그룹, 화면 약 120개를 가진 어학원 ERP다. 학생 등록부터 침대 배정, 출석, 시험, 입금 매칭, 포인트, 경비 출입까지 이미 다루고 있어, 설계표에서 새로 만들려던 기능의 상당수가 업체 DB에 이력으로 쌓여 있다.

- **기술 구조**: CodeIgniter(PHP) 계열이다. 주소가 /appl/adm/기능/화면 형식이고 폼에 csrf\_test\_name이 있다. DB는 MySQL 계열로 추정한다. 에이전시 요청 화면에 'EduX'라는 이름이 보여 업체명으로 추정한다.
- **테이블 이름이 드러나 있다**: 입력 항목이 '테이블 약어\_항목' 형식이다(st\_name, tr\_state, roo\_floor). 화면 84개의 항목 이름에서 테이블 약 50개와 주요 열을 읽어냈다. 학생 개인정보는 열람하지 않고 구조만 읽었다.
- **학생과 연수가 나뉜다**: 학생(st\_id)과 연수(tr\_id)가 별개다. 연장·복귀하면 한 학생에 연수 기록이 여러 개 생긴다. 입학은 격주 배치(예: 288\_A 2026-11-15, 288\_B 2026-11-29)로 묶인다.
- **규모와 이력**: 기숙사 타입이 2010-01-01부터 있고 배치 번호는 315까지 만들어져 있다. 캠퍼스는 Challenger, Premium, MCO 3곳이다.
- **다국어·다통화**: 기준 테이블에 이름이 6개 언어(en, ko, jp, ch, tw, vi)로 있다. 가격은 원·달러·엔·페소 4개 통화이고 은행 계좌는 5개다.
- **사용자 4종**: 직원(sf), 교사(te, 모바일 앱 설치 여부 관리), 학생(st), 에이전시 담당자(am)가 각자 로그인한다. 메뉴에 '에이전시 공유' 설정이 있어 에이전시 화면도 같은 시스템이다.

이 분석이 기획에 주는 결론은 네 가지다.

1. **그대로 옮길 뼈대**: 기준 코드, 학생·연수·배치, 기숙사·교실, 에이전시, 사람·조직.
2. **설계표와 겹치는 것**: 출석·시험·위반·외출·경비는 업체 DB에 이미 이력이 있다. 새 LMS와 인트라넷은 이 테이블을 이어받아야 학생 기록이 끊기지 않는다.
3. **설계표에 없는 것**: 연수 개념, 회계·포인트·POS, 프로모션, 비자 보고. 새로 설계에 넣을지, 업체 포털에 남길지 정해야 한다.
4. **설계표를 고칠 것**: 설계표는 student\_no 하나를 기준 키로 쓰지만, 업체는 출석을 학생 기준으로, 옵션 클래스·여행·인보이스를 연수 기준으로 저장한다. 공용 DB에 enrollments(연수) 테이블을 추가한다.

## 목표 아키텍처

모든 화면은 Cloudflare에서 서비스하고, 모든 데이터는 Supabase 공용 DB 한 곳에 둔다. 화면 코드와 DB 변경은 GitHub 저장소 하나에서 관리하고 자동으로 배포한다.

> 다이어그램(목표 아키텍처 · 화면 4개, 공용 DB 1개)은 [원본 문서](https://claude.ai/artifact/9JTCwocjZJFqPjdDjvZEg2)에서 볼 수 있다.

화면은 RLS가 걸린 공개 키로만 DB를 읽고 쓴다. 모든 권한을 가진 서비스 키는 Workers만 쓰고, 업체 포털 반출 파일도 Workers가 legacy에 적재한다.

| 서비스 | 맡는 일 | 비용 |
| --- | --- | --- |
| Supabase Pro | 공용 DB, 로그인, 파일, RLS, 일일 백업. 운영·테스트 프로젝트 2개 | 월 25달러 + 테스트 약 10달러 (도입 계획안 기준) |
| Cloudflare | 화면 4개 호스팅(Pages), 서버 작업(Workers), 도메인·봇 차단 | 무료 플랜으로 시작, Workers 유료는 월 5달러 |
| GitHub | 저장소 1개, Actions로 테스트·배포, 이슈로 요청 관리 | 무료 Organization으로 시작 |

- **화면**: TypeScript + React(Vite). 화면 문구는 번역 파일로 분리해 업체와 같은 6개 언어를 지원한다(P7).
- **저장소 구조**: apps/portal, apps/student, apps/partner, apps/intranet, workers, supabase/migrations, packages/ui. LMS도 같은 supabase/migrations를 따른다.
- **DB 변경 순서**: PR → 리뷰 → 테스트 DB 자동 적용 → 확인 후 운영 DB(원칙 공동 개발 약속 5번).

## DB 이관 전략

업체 DB를 원본 그대로 `legacy` 영역에 복사하고, 설계표 이름 규칙을 따르는 `public` 영역으로 옮겨 담는 두 층 구조로 간다. 원본을 바꾸지 않으니 언제든 다시 맞춰 볼 수 있고, 새 화면은 설계표 이름만 본다.

1. **포털에서 직접 추출**: 업체에 요청하지 않고, 관리자 계정으로 업체 포털의 목록 조회 API(이름이 \_load로 끝나는 주소)를 읽어 JSON으로 저장한다. 저장·삭제 기능은 호출하지 않는다(11/7 결정).
2. **추출 범위**: 학생(졸업생·재학생·입학 예정), 학생별 회계(인보이스·입금·포인트), 기숙사 배정, 학생 메모, 에이전시와 에이전트 계정.
3. **민감 항목 제외**: 비밀번호 필드(에이전트 am\_pw 등)와 세션 토큰 필드는 저장하지 않는다. 에이전트 비밀번호는 새 포털에서 필요할 때 재등록한다.
4. **보관과 적재**: 추출 파일은 GitHub에 올리지 않는 로컬 폴더에 둔다. 테스트 DB에는 이름·연락처·여권을 가린 사본을 legacy 스키마로 넣어 매핑을 개발하고, 실제 데이터는 보안 점검(관문 2)을 통과한 뒤 운영 DB에 넣는다.
5. **테이블 판정**: 추출한 데이터셋마다 유지·통합·삭제를 정한다. 기준은 '데이터 모델' 절을 따른다.
6. **매핑**: legacy에서 public으로 바꾸는 SQL을 GitHub에 버전으로 남긴다. 예: st → students, tr → enrollments, roo·bed → rooms·beds. 6개 언어 이름 열은 name\_i18n(json) 하나로, \*\_yn 플래그는 true/false로 바꾼다.
7. **검증**: 추출 건수를 화면의 전체 건수와 맞춘다(11/7 1차 추출: 학생 5,537 · 연수 5,534 · 인보이스 5,524 · 입금 679 · 포인트 내역 14,439 · 기숙사 배정 4,906 · 메모 4,872 · 에이전시 651 · 에이전트 640. 인보이스 10건 차이는 확인 필요). 포인트 잔액 합계도 화면 숫자와 맞춰 본다.
8. **병행 운영**: 업체 포털을 쓰는 동안에는 같은 추출을 정기적으로 다시 돌려 legacy를 갱신한다.
9. **모듈별 전환**: 모듈 하나씩 쓰기 담당을 JIC 포털로 넘기고, 그 모듈의 업체 메뉴는 사용을 멈춘다. 마지막 모듈이 넘어가면 최종 추출본을 보관하고 업체 포털을 해지한다.

추출은 관리자 화면이 쓰는 조회 API를 그대로 읽는다. 그래서 업체가 화면을 바꾸면 추출 스크립트도 고쳐야 하고, 화면에 없는 항목은 빠질 수 있다. 요청 사이에 간격을 두어 서버에 부담을 주지 않고, 업체 이용약관에 자동 조회 제한이 있는지 확인한다.

이 방향을 따르려면 원칙 다섯 개를 고쳐야 한다. V1(업체 포털이 기준)은 '전환 전까지 기준'으로, V2(2주 엑셀)는 '병행 운영 수단'으로, V5(API)는 '관리자 조회 API로 자체 추출'로, V6(시간표 2차)는 전환 로드맵으로, C3(기준 키)는 학생 번호 + 연수 번호로 바꾼다.

## 데이터 모델

공용 DB는 설계표 40개에 업체에서 가져올 테이블을 더해 약 85개, 9개 그룹이 된다. 중심은 학생(students) 하나에 연수(enrollments)가 여러 개 달리는 구조다. 연수는 배치·코스·기숙사 타입을 가지고, 침대 배정·인보이스·옵션 클래스가 연수에 붙는다. 테이블 이름은 제안이며 LMS 담당자와 합의해 확정한다.

| 그룹 | 테이블 (제안) | 출처 | 전환 후 쓰기 담당 |
| --- | --- | --- | --- |
| 기준 코드 (11) | academies, campuses, courses, course\_prices, dorm\_types, dorm\_prices, extra\_fees, exchange\_rates, bank\_accounts, codes, holidays | 업체 | JIC 포털 관리자 |
| 학생·연수 (9) | students, **enrollments**, **batches**, enrollment\_groups, family\_registrations, family\_members, student\_consents, upload\_logs, visa\_reports | 업체 + 설계표 | JIC 포털 (마케팅·오피스) |
| 등록·변경 (4) | change\_requests, guest\_requests, promotions, promotion\_rules | 업체 | JIC 포털 (마케팅) |
| 기숙사·교실 (6) | rooms, beds, room\_assignments, room\_blocks, room\_targets, classrooms | 업체 | JIC 포털 (오피스) |
| 학업 (18) | class\_sessions, class\_enrollments, attendance, attendance\_closings, option\_classes, option\_class\_members, self\_study\_sessions, weekend\_study, absence\_requests, test\_types, test\_results, cefr\_mappings, reports, recordings, daily\_recall, class\_change\_requests, study\_goals, materials | 설계표 + 업체 이력 | LMS (신청은 학생 포털) |
| 생활 (13) | penalty\_rules, penalties, counseling\_notes, outings, incident\_reports, keycards, overnight\_permissions, curfew\_checks, photos, nonacademic\_requests, internal\_notices, forms, approvals | 설계표 + 업체 이력 | 인트라넷 (외출·귀가는 가드) |
| 회계 (7) | invoices, deposits, invoice\_matchings, point\_ledger, pos\_products, pos\_sales, agency\_commissions | 업체 | 학생별 회계 이력은 이관 확정(11/7), 운영 화면은 결정 필요 |

| 사람·권한 (7) | users, user\_roles, staff, positions, departments, staff\_assignments, audit\_logs | 설계표 + 업체 | JIC 포털 관리자 |

설계표 공동 개발 약속(snake\_case, student\_no·campus\_id, created\_at·updated\_at·created\_by)은 그대로 따른다. 여기에 두 가지를 더한다.

- **연수 번호**: 연수 단위 기록(침대 배정, 인보이스, 옵션 클래스, 여행)에는 enrollment\_id를 넣는다. student\_no는 업체 학생 번호를 그대로 쓴다.
- **추적 열**: 업체에서 온 행에는 legacy\_id를 남겨, 전환 뒤에도 원본 행을 찾을 수 있게 한다.

## 기능 범위

업체 메뉴 15개 그룹은 그대로 옮길 것, 설계표 기능으로 바꿀 것, 없앨 것으로 나뉘고, 설계표에만 있는 기능이 새로 더해진다. 판정은 초안이며, 메뉴별 사용 빈도를 담당자에게 확인해 확정한다.

## 권한·보안

권한은 화면이 아니라 DB가 막는다. 설계표의 역할별 권한 표를 Supabase RLS(행 단위 보안) 정책으로 그대로 옮기고, 실제 학생 정보를 넣기 전에 점검을 통과해야 한다(C12).

| 영역 | 방식 |
| --- | --- |
| 역할 | 설계표의 9개 역할에 'JIC 포털 관리(오피스)'가 기준 정보 쓰기를 맡는다. user\_roles에 역할·캠퍼스·등급·부서·에이전시 지점을 둔다 |
| RLS | 모든 테이블 RLS 켜기. '본인', '지점', '담당', '캠퍼스' 범위를 판단하는 공통 함수를 만들고 정책에서 재사용 |
| 직원 로그인 | 회사 구글 계정 로그인(구글 드라이브를 이미 쓴다). 한 번 로그인으로 LMS·인트라넷·JIC 포털을 오간다(C6) |
| 학생 로그인 | 학생 번호 + 초기 비밀번호(생년월일), 첫 로그인 때 변경 강제(V4). 계정 생성은 서버(Worker)에서만 한다 |
| 에이전시·가드 | 에이전시는 지점 단위 계정, 관리자 승인 후 활성. 업체 포털의 에이전트 계정은 옮기되 비밀번호는 재등록한다. 가드는 외출·귀가 화면만 여는 계정(방식 미결정) |
| 비밀 키 | 서비스 키(모든 권한)는 Cloudflare Worker 비밀 변수에만 둔다. 브라우저와 GitHub 코드에는 공개 키만 |
| 접근 기록 | 상담 기록 열람(I5), 업로드, 권한 변경을 audit\_logs 테이블에 남긴다 |
| 백업 | Pro 플랜의 일일 백업 + 월 1회 별도 덤프를 회사 드라이브에 보관. 복원 테스트를 전환 전 1회 한다 |
| 로그인 보호 | Cloudflare WAF와 Turnstile로 로그인·등록 신청 화면의 봇을 막는다 |

연락처·여권 등 민감 항목이 업체 DB에 있다면 열 단위로 가리는 뷰를 만들고, 동의서 문구는 법률 검토 후 확정한다(미결정 5번).

## 로드맵

제안 일정은 회계를 뺀 6단계가 약 32주(8개월)이며, 실제 학생 정보는 보안 점검을 통과한 뒤에만 공용 DB에 들어간다. 원칙 C9의 개발 순서(파트너 포털 → LMS → 학생 포털 → 인트라넷)는 유지하고, 앞에 뼈대 단계를, LMS 뒤에 업체 기능을 옮기는 운영 이전 단계를 넣었다.

> 다이어그램(로드맵 · 7단계, 관문 4개)은 [원본 문서](https://claude.ai/artifact/9JTCwocjZJFqPjdDjvZEg2)에서 볼 수 있다.

LMS는 필리핀 담당자가 따로 개발하므로 2단계와 겹쳐 진행할 수 있고, 그러면 전체 기간이 줄어든다. 각 단계가 끝날 때마다 해당 업체 메뉴의 사용을 멈춘다.

## 리스크와 확인 필요 사항

업체 협조 없이 추출하므로, 가장 큰 리스크는 화면이 바뀌어 추출이 끊기거나 항목이 빠지는 것이다. 나머지는 전환 순서와 검증으로 관리할 수 있다.

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| 업체가 화면이나 조회 API를 바꾼다 | 정기 추출이 멈춘다 | 추출할 때마다 건수를 화면 전체 건수와 대조한다. 실패하면 메뉴별 엑셀 내보내기로 보완한다 |
| 실제 DB 구조가 화면 분석과 다르다 | 매핑을 다시 해야 한다 | 조회 API에 없는 항목은 빠진다. 화면별로 대조해 빠진 항목을 추가로 추출한다 |
| 병행 기간에 두 곳에 입력한다 | 값이 어긋난다 | 테이블마다 쓰기 담당은 한 곳. 모듈 단위로 전환하고 전환일을 공지한다 |
| 업체 해지 후 학생 번호 발급 | 신입생 번호가 없어진다 | JIC 포털이 업체 번호 체계를 이어서 발급한다 |
| 교사 모바일 앱 | 업체 앱을 끄면 출석 입력 수단이 없다 | LMS 휴대폰 화면(L7)이 준비된 뒤에 출석 모듈을 전환한다 |
| 회계 데이터 오류 | 잔액·환불이 틀린다 | 회계는 마지막에, 잔액 합계를 대사한 뒤 전환한다 |
| 필리핀 정부 보고(비자·학교 보고) | 보고가 빠진다 | 보고 항목을 그대로 옮기고, 전환 전 보고서를 양쪽에서 뽑아 비교한다 |
| 여권·연락처 같은 개인정보 | 유출 | RLS, 실제 데이터 투입 전 보안 점검, 필리핀 개인정보보호법(Data Privacy Act 2012) 확인 |
| LMS 담당자와 테이블이 어긋난다 | 연결이 깨진다 | 마이그레이션을 GitHub 한 곳에서 관리하고, 변경은 PR로 합의한다 |
| 업체 화면·코드를 베낀다는 문제 제기 | 저작권 분쟁 | 데이터와 구조만 옮기고, 화면과 코드는 새로 작성한다 |
