# 인트라넷 (`apps/intranet`)

직원용 화면과 경비실 가드 태블릿이다. 디자인은 `docs/design/IntranetPenalty.dc.html`(I1 패널티 승인)과 `GuardTablet.dc.html`(I2 외출·귀가 가드 태블릿, 1180×820)을 따른다. 로컬 개발 서버로 개발하고, 배포는 Cloudflare Workers 하나로 한다(아래 '배포', 직원 화면·가드 태블릿 서버 코드 11/8, Cloudflare 설정 전).

## 실행

```powershell
npm install
npm run intranet
```

http://127.0.0.1:5177 을 연다. 가드 태블릿은 http://127.0.0.1:5177/guard (외출·귀가 화면의 '가드 태블릿 열기'). 로컬에는 로그인이 없다(관리자 앱과 같다).

## 규칙

### 외출·귀가 (가드 태블릿)

- 재학생 명단(관리자 core의 '재학' 분류)에 있는 학생만 기록한다. 졸업생·입학 예정자는 "재학생 명단에 없는 번호입니다."
- **카드키 QR**(학생 앱 '출입 QR', 1분마다 바뀜, `apps/student/server/keycard.ts`): **카메라로 읽기**를 켜면 태블릿 카메라로 읽는다(앞·뒤 카메라 바꾸기, 이 기기에 기억). 브라우저 내장 QR 읽기가 있으면 쓰고, 없으면(아이패드 Safari 등) jsQR 로 읽는다. 같은 QR은 30초 동안 한 번만 처리한다. 카메라는 https 주소에서만 열린다.
- USB·블루투스 QR 스캐너도 그대로 된다: 학생번호 칸에 QR 값을 넣고 Enter를 보내면 처리된다. 학생번호 칸에는 항상 커서가 있다.
- QR은 서명과 시각을 확인한다. 지금·직전 1분 창만 받고(오래된 QR '시간이 지난 QR', 서명이 틀리면 '올바른 카드키 QR이 아님'), 숫자만 넣으면 직접 입력한 학생번호로 본다. 기록에 찍은 방법(QR / 번호 입력)이 남고, 외출·귀가 목록과 방금 처리 칸에 '번호 입력'이 보인다.
- 외출: 이미 외출 중이면 거절한다(외출 시각을 보여 주고 귀가로 처리하라고 안내).
- 귀가: 외출 기록이 없어도 귀가는 남긴다. 통금 확인에 필요하기 때문이며, 목록에 '외출 기록 없음'으로 보인다.
- 설정에 근무자가 있으면 근무자를 골라야 기록된다. 이 기기에서 고른 캠퍼스·근무자·외출/귀가는 기기에 기억한다.

### 통금 판정

- 시각은 필리핀 시간(UTC+8) 기준이다. 저장은 ISO(UTC).
- 외출·귀가는 '밤' 단위로 묶는다. **오전 5시 전 기록은 전날 밤**이다(예: 11/8 01:10 귀가 → 11/7 밤).
- **승인된 외박이 있는 밤은 통금 위반이 아니다.** 외출 기록과 가드 태블릿에 '외박 허용 ~복귀일'로 보인다. 1박 이상 학교 여행에 참가 신청한 학생도 같다('외박 허용 ~돌아오는 날 (학교 여행)').
- 그 밖에 그날 밤 통금 시각(설정, 처음 값 23:00)보다 늦게 외출했거나, 늦게 귀가했거나, 통금이 지나도 귀가하지 않았으면 통금 위반이다. 근거 문장 예: `통금 23:00, 귀가 23:41`, `통금 23:00 이후 외출 23:20, 귀가 23:55`, `통금 23:00, 미귀가`, `통금 23:00, 귀가 01:30 (외출 기록 없음)`.

### 공항 이동 배차 (귀국 일정)

- 학생이 귀국 항공편에서 '공항 이동 차량 요청'을 하면 '요청'으로 보인다. '처리'에서 **배차 확정**(기숙사 출발: 출발일 또는 전날 + 시각, 메모: 차량·집합 장소) 또는 **배차 불가**(사유 필수)로 처리한다. 메모는 학생 앱에 보인다.
- 기숙사 출발이 비행기 출발보다 늦으면 거절한다. 처리자(오른쪽 위 직원 이름)와 시각이 남고, 다시 처리하면 덮어쓴다. 출발일이 지난 항공편은 처리하지 않는다.
- 처리 뒤 학생이 출발일·시각을 바꾸면 **재확인 필요**, 차량 요청을 빼면 **요청 취소**로 보인다. 메뉴의 숫자는 오늘 이후 출발 중 요청·재확인 건수.
- 배차 기록(직원이 씀)과 항공편(학생이 씀)은 따로 저장한다(기획안 C2). 모양과 규칙은 `apps/student/server/departures.ts`.

### 가드 리포트 (업체 eni, 기획안 incident_reports)

- 가드 태블릿의 '사건 리포트 작성'에서 학생번호(방금 처리한 학생이 미리 들어감), 종류, 내용(500자), 발생 시각(비우면 지금)을 받는다. 종류는 업체 포털과 같은 음주·폭력·무단외출·기타.
- 발생 시각이 지금보다 뒤면 전날로 본다(자정 넘어 쓰는 리포트). 재학생만, 설정에 근무자가 있으면 근무자를 골라야 등록된다.
- 등록하면 **패널티 승인 대기 후보가 바로 생긴다**(출처: 가드 리포트). 종류가 그대로 점수표 종류가 된다(음주·폭력·무단외출·기타, 11/10 결정 I7로 폭력·무단외출을 점수표에 따로 뒀다. `20261110103000_intranet_decisions_2.sql`). 근거는 `가드 리포트(22:40): 음주 — 내용 앞 60자`, 발생일은 통금과 같은 '밤' 기준.
- 리포트는 고치거나 지우지 않는다. 잘못 쓴 리포트는 패널티를 반려한다(통금 후보 정리는 가드 리포트 패널티를 건드리지 않는다).

### 학교 여행 (업체 'Outing > Travel'의 tra 여행 / trt 신청자)

- 직원이 여행을 올리고 학생이 학생 앱에서 참가 신청·취소한다. 모양과 규칙은 `apps/student/server/trips.ts` 한 곳이다.
- 등록: 제목·장소 필수(100자), 집합(100자)·안내(1000자) 선택. 새 여행은 출발일이 오늘 이후, 돌아오는 날은 출발일과 같거나 뒤(14박까지), 신청 마감일은 출발일과 같거나 앞, 정원 1~500명, 비용 0 이상(PHP, 0 = 무료). 대상 캠퍼스를 비우면 전체 캠퍼스.
- 수정: 지난 여행도 고칠 수 있다(기록 정리). 정원은 이미 신청한 학생 수보다 줄일 수 없다. 취소한 여행은 고치거나 되돌리지 않는다(학생 앱에 '여행 취소'로 보인다).
- 상태: 신청 받는 중 ↔ 신청 마감(직원이 일찍 닫음), 여행 취소. 신청 마감일이 지나면 상태와 상관없이 학생은 신청·취소하지 못한다.
- 명단: 참가 신청(신청 순) → 대기(대기 순서 'N번', 11/10 결정 I12) → 취소·제외 순. 위에 '신청 N명 · 대기 N명'. 참가가 빠지거나 정원을 늘리면 대기자가 신청 순서대로 참가로 올라간다(`20261110140000_trip_waitlist.sql`).
- 명단에서 빼기: 참가·대기 신청, 사유 필수(300자, 학생에게 보인다). 처리자는 로컬은 오른쪽 위 이름, 배포는 로그인한 직원. 다시 넣으려면 학생이 다시 신청한다.
- **외박 허용**: 1박 이상 여행의 참가 신청은 승인된 외박과 같이 본다(출발일 밤 ~ 돌아오는 날 전날 밤). 통금 확인·가드 태블릿·Student File·홈의 '오늘 밤 외박'에 들어가고, 신청 처리의 외박 목록에는 들어가지 않는다. 학생 취소·명단 제외·여행 취소·날짜 변경은 통금 위반 후보에 바로 반영한다.

### 학생 계정 (학생 앱 로그인)

- 규칙은 학생 앱과 같다(`apps/student/server/accounts.ts`): 아이디 = 학생번호, 첫 비밀번호 = 생년월일 8자리, 첫 로그인 때 새 비밀번호를 정한다. 대상은 재학·입학 예정 학생.
- **만들기**: 계정 없는 학생을 한 번에 8명씩 만든다(Cloudflare 무료 요금제의 요청당 외부 호출 한도 때문에 나누고, 화면이 남은 수가 0이 될 때까지 이어서 부른다). 계정만 있고 연결이 빠진 학생은 잇기만 한다. 생년월일이 없는 학생은 만들지 않는다.
- **비밀번호 초기화**: 학생이 비밀번호를 잊었을 때 생년월일로 되돌리고 다음 로그인 때 다시 바꾸게 한다.
- 계정 작업은 배포 서버가 서비스 키로 Supabase Auth Admin API 를 부른다(`apps/student/server/accountAdmin.ts`, 계정 생성 스크립트 `npm run student:accounts` 와 같은 코드). 서비스 키가 없으면 안내만 보인다. 로컬 개발 서버에는 계정이 없다(학생 앱이 학생번호 + 생년월일로 로그인).
- 만들기·초기화는 **접근 기록**에 남는다(처리자 = 로그인한 직원, DB 함수 `student_account_audit`). 직원(관리자·오피스)이면 할 수 있다(11/9 결정 I4).

### 가드 계정 (출입구 공용 계정)

- 출입구마다 하나(11/8 결정). 출입구 이름(40자, 가드 기록의 처리자로 보임), 캠퍼스(그 출입구로 고정), 로그인 이메일, 비밀번호(8~72자, 영문과 숫자, 확인 칸)를 받는다. 이메일로 메일은 보내지 않는다.
- 비밀번호 바꾸기·지우기는 이 화면에서 만든 가드 계정만 된다(직원·학생 계정 id 로는 404). 지우면 그 태블릿은 다시 로그인하지 못하고, 지난 외출·귀가 기록은 남는다.
- 계정 작업은 배포 서버가 서비스 키로 한다(`apps/intranet/server/guardAccounts.ts`: Auth Admin API + `guard_accounts`). 만들기·비밀번호·지우기는 접근 기록에 남는다(DB 함수 `guard_account_audit`, 대상 = 출입구 이름).
- **관리자만** 쓴다(11/9 결정 I4). 오피스에게는 메뉴가 숨고, 주소로 열거나 API를 바로 불러도 서버가 `403 admin_only`, 접근 기록 함수도 관리자만 받는다(`20261109170000_intranet_decisions.sql`).

### 생활 요청 (업체 '요청사항(학생)'·'ID 카드 교체', 기획안 nonacademic_requests)

- 학생 앱이 쓰는 요청 데이터를 그대로 읽고 처리한다. 모양과 규칙은 `apps/student/server/lifeRequests.ts` 한 곳이다.
- 접수 → 처리 중 → 완료·반려. 끝난 요청(완료·반려·학생 취소)은 바꾸지 않는다. 반려는 답변에 사유를 적어야 한다. 답변을 비우고 완료하면 지난 답변이 그대로 남는다.
- 처리할 목록(접수·처리 중)은 오래된 순, 끝난 목록은 최근 처리 순이다. 메뉴·홈에 접수 건수가 보이고, Student File에 그 학생의 요청이 보인다.
- 처리자는 로컬은 오른쪽 위에 입력한 이름(없으면 비워 둠), 배포는 로그인한 직원이다.

### 신청 처리 (결석·외박)

- 학생 앱이 쓰는 신청 데이터를 그대로 읽고 고친다. 모양과 규칙은 `apps/student/server/requests.ts` 한 곳이다.
- 대기 중인 신청만 승인·반려된다. 학생이 이미 취소한 건은 건너뛰고 몇 건을 건너뛰었는지 알려 준다.
- 처리 메모(300자)는 학생 앱 신청 상세에 '담당자 메모'로 보인다. 반려 사유를 적는다.
- 대기 목록은 날짜가 가까운 순(처리할 순서), 처리된 목록은 최근 처리 순이다. 메뉴에 대기 건수가 보인다.

### 내부 공지 (기획안 I10, 업체 게시판 → 내부 공지)

- 대상은 전체 또는 캠퍼스 하나. 캠퍼스로 보면 그 캠퍼스 공지와 전체 공지가 함께 보인다.
- (11/10 결정 I14) 대상 역할(관리자·오피스·매니저)을 고를 수 있다. 고르지 않거나 셋 다 고르면 모든 역할. 관리자는 모든 공지를 보고, 오피스·매니저는 대상 역할이 비었거나 자기 역할이 든 공지만 목록·상세·홈에 보인다. 보여 주는 범위이고 비밀 범위는 아니다(`internal_notices.roles`, `20261110123000_notice_roles.sql`).
- 게시 종료일이 지나면 '지난 공지'로 넘어간다. 수정에서 종료일을 지난 날로 바꾸면 바로 내려간다. 삭제 기능은 두지 않았다.
- 직원이 공지를 열면 읽음(이름·시각)이 직원마다 한 번 남는다. 이름을 입력하지 않았으면 읽음이 남지 않는다. 메뉴와 홈에 이 직원이 안 읽은 게시 중 공지 수가 보인다.
- 작성·수정에는 오른쪽 위 직원 이름이 필요하다(상담 기록과 같다).

### 상담 기록·접근 기록 (기획안 I5, 권한·보안 '접근 기록')

- 목록·Student File·접근 기록에는 **제목만** 내보낸다. 내용은 상세에서만 보이고, 상세를 열 때마다 '열람'을 남긴다. 같은 직원이 같은 기록을 10초 안에 다시 열면(새로고침 등) 한 번으로 센다.
- 작성·수정·후속 조치 완료·되돌림도 남긴다. 접근 기록은 추가만 되고 고치거나 지울 수 없다. 상담 기록 삭제 기능은 두지 않았다.
- 검색은 학생·제목·작성자만 된다. 내용 검색은 사실상 열람이라 넣지 않았다.
- 후속 조치 기한이 있으면 '확인할 일'에 들어가고, 기한이 지나면 빨갛게 보인다. 메뉴에는 기한이 오늘이거나 지난 건수, 홈에는 열린 건수가 보인다. 기한을 바꾸면 다시 열린 상태가 된다.
- 처리자: 로컬에는 로그인이 없어 **오른쪽 위에 입력한 직원 이름**(브라우저에 저장)을 쓴다. 이름이 없으면 상담 기록을 열거나 쓸 수 없다. 배포에서는 로그인한 직원으로 바꾼다.
- 상담 분류(학업·생활 등)와 공개 범위는 정해지지 않아 만들지 않았다. 제목에 자유롭게 쓴다.

### 패널티

- 통금 위반은 외출 기록에서 **승인 대기 후보로 자동으로 올라간다**(출처: 외출 기록). 같은 외출 기록으로는 한 건만 생긴다.
- 승인 대기 중인 후보는 다시 계산한다. 미귀가였다가 귀가하면 근거가 바뀌고, 통금 시각을 늦추거나 그 밤의 외박을 승인해 더는 위반이 아니면 후보에서 빠진다. 승인·반려한 건은 바뀌지 않는다.
- 점수는 점수표에서 가져온다. **비어 있으면 '점수 미정'**으로 보이고, 그대로 승인하면 0점으로 센다. 승인할 때의 점수를 그 건에 남기므로, 나중에 점수표를 바꿔도 이미 승인한 점수는 그대로다.
- '승인 후 누적'은 그 학생의 승인된 점수 합계 + 이 건의 점수, 경고 단계는 점수표 기준으로 `- → 1단계`처럼 바뀌는 단계를 보여 준다. 기준이 비어 있으면 '기준 미정'.
- 위반 종류는 디자인의 4가지(무단결석, 통금 위반, 음주, 기타)다. 통금 위반은 외출 기록에서, 음주·기타는 가드 리포트에서, 무단결석은 강사 포털 출석에서 후보가 생긴다.
- **무단결석**(11/9, 출처: 출석 기록): 강사 포털 출석(`attendance`, 강사 포털이 쓰고 인트라넷은 읽기만)에서 **학생·날짜당 한 건**을 만든다. 규칙은 `server/core.ts` `syncAbsencePenalties` 한 곳이다.
  - **출석이 마감된 날**(캠퍼스·날짜, 강사 포털 매니저·관리자가 마감)의 결석만 센다. 체크 중인 날은 후보가 없다.
  - 강사 포털에서 **사유 인정**한 수업은 빼고, 남은 결석 수업을 시각 순으로 근거에 적는다(예: `수업 결석 2회(08:00 Grammar, 13:00 Speaking)`).
  - 그날 **승인됐거나 처리 전인 결석 신청**이 있으면 만들지 않는다(처리 전이면 처리된 뒤에 다시 본다). 결석 신청의 교시와 수업 시각을 잇는 기준이 아직 없어서 신청이 있으면 날 전체를 뺀다. 반려된 신청은 근거 끝에 `결석 신청 반려`로 적는다.
  - 참가 신청한 **학교 여행 날**(출발일~돌아오는 날)도 뺀다.
  - 직원이 홈·패널티·Student File을 열 때 지난 31일(`ABSENCE_LOOKBACK_DAYS`)을 다시 맞춘다. 통금 후보처럼 승인 대기 중인 후보는 사유 인정·신청 승인·마감 되돌리기로 무단결석이 아니게 되면 지워지고, 승인·반려한 건과 31일보다 오래된 건은 그대로다.
  - 로컬에는 강사 포털 실행이 없어 출석이 비어 있다. 시험하려면 `.local-db/intranet/attendance-sample.ndjson`에 수업 한 건을 한 줄로 넣는다: `{"stId":"30161","day":"2026-11-08","time":"08:00","campus":"Challenger","subject":"Grammar","excused":false,"closed":true}`. `result`(`AT`·`AB`·`TA`·`null`, 없으면 결석)·`teacher`·`room`·`lateMin`을 더하면 Student File '수업 출석'에도 보인다.

### Student File '수업 출석' (11/9)

- 강사 포털 출석에서 그 학생의 지난 30일(`ATTENDANCE_DAYS`) 수업을 읽어, 합계(수업·출석·지각과 지각 분·결석·체크 전)와 결석·지각 목록(최근 30건)을 보인다. 출석과 사유 인정은 강사 포털이 정하고 인트라넷은 읽기만 한다.
- 결석의 사유: 강사 포털 **사유 인정** → 그날 **결석 신청 승인** → **신청 처리 전** → **무단** 순으로 붙인다. 반려된 신청은 무단이다. 신청의 교시와 수업 시각은 아직 잇지 않아 그날 신청을 그날 결석에 붙인다(강사 포털 `lms_attendance_summary`와 같은 기준, `docs/leo-todo.md` I2). 여기의 '무단'은 마감 전 결석도 세므로, 무단결석 패널티 후보(마감된 날만)와 수가 다를 수 있다.
- 배포: 강사 포털 함수 `lms_student_attendance(학생, 시작, 끝)`(강사 포털 사용자 = 직원·매니저). 못 읽으면 이 칸만 비우고 나머지는 그대로 연다. 규칙은 `server/core.ts` `attendanceSummary`.

### 직원 역할 (docs/roles.md, 11/9 레오님 승인)

인트라넷 칸 중 관리자·오피스 구분(2단계 A), 매니저(2단계 B), 매니저의 상담 기록(2단계 C)을 넣었다. 권한표에 없던 것은 11/9 밤 결정(I4·I5, `docs/leo-todo.md`)대로 했다.
- **관리자·오피스**: 관리자 포털 '사용자·권한'에서 주는 `user_roles`의 역할로 나눈다. `admin`이 있거나 `office`가 없으면 관리자다(DB `is_admin()`과 같음). 역할을 주기 전에는 모든 직원이 관리자라 지금과 같다.
- **관리자만**: 패널티 점수표 저장, 접근 기록 보기, 가드 계정(I4). 오피스에게는 점수표가 읽기로만 보이고(저장 버튼 없음) 접근 기록·가드 계정 메뉴가 숨는다. 주소로 열거나 API를 바로 불러도 서버가 `403 admin_only`로 막고, DB(`20261109070000_intranet_roles.sql`, 가드 계정 접근 기록은 `20261109170000_intranet_decisions.sql`)도 막는다.
- **Student File**: 오피스는 맡은 캠퍼스(오피스 역할의 캠퍼스, 빈칸이면 모든 캠퍼스) 학생만 목록에 나오고, 다른 캠퍼스 학생 상세는 `403 campus_forbidden`이다. 외출·패널티·신청 목록은 권한표대로 오피스도 모든 캠퍼스를 본다.
- **상담 기록·접근 기록의 캠퍼스**(11/10 결정 I16): 맡은 캠퍼스는 `user_roles` 한 곳이다. 관리자는 모든 캠퍼스, 오피스는 오피스 역할의 캠퍼스(빈칸이면 모든 캠퍼스). DB `staff_has_campus()`가 이 기준이고(`20261110103000_intranet_decisions_2.sql`), `staff_campuses` 표는 더 쓰지 않는다. 학생 계정 화면은 직원(관리자·오피스) 모두 쓴다(I4).
- 로컬(로그인 없음)은 관리자로 본다.
- **매니저**(강사 포털 `user_roles` manager, 직원 아님, 11/9): 인트라넷 일부만 연다. 직원이면서 매니저 역할도 있으면 직원 권한 그대로다.
  - 열리는 화면: 홈, 내부 공지(읽기·쓰기, 고치기는 자기 글만), Student File(맡은 캠퍼스), 상담 기록(매니저 역할의 캠퍼스, 빈칸이면 모든 캠퍼스. 작성자·접근 기록 이름은 강사 목록 이름, `20261109110000_intranet_manager_counseling.sql`), 패널티 승인, 패널티 점수표(읽기), 외출·귀가, 통금 확인, 가드 리포트, 결석 신청 처리, 학교 여행(읽기). 메뉴에는 이것만 보이고 홈에서도 열 수 없는 화면의 칸은 숨는다. 접근 기록은 관리자만 보므로 매니저의 상담 상세에는 열람 기록 목록이 비어 보인다.
  - 패널티 승인·반려는 **무단결석만**('정할 것' 4, 수업 관련 위반), 그리고 **맡은 캠퍼스만**(매니저 역할의 캠퍼스, 빈칸이면 모든 캠퍼스, 11/9 결정 I5). 다른 종류·다른 캠퍼스 건은 목록에 보이지만 버튼이 없고 API는 `403 manager_absence_only`·`403 campus_forbidden`, DB 정책 `penalties_manager_decide`도 같은 범위만 고치게 한다(`20261109170000_intranet_decisions.sql`). 무단결석 후보는 매니저가 화면을 열 때도 정리한다(통금 후보는 직원 화면에서). 후보 정리(대기 건 넣기·지우기)는 캠퍼스를 가리지 않는다.
  - 결석 신청 처리는 매니저·오피스 둘 다('정할 것' 3), 같은 함수 `decide_absence_requests`(처리자 = 로그인한 사람).
  - 나머지 경로는 서버가 `403 manager_forbidden`. 매니저는 업체 원본(`legacy_*`)을 못 읽어서 서버가 가드처럼 **서비스 키**로 읽고 허용한 경로로만 내보낸다(서비스 키가 없으면 매니저 요청은 `500 server_config`). 외박은 승인된 것만 사유 없이 읽는다. 쓰기는 매니저 토큰이라 DB(`20261109100000_intranet_manager.sql`)가 같은 범위만 허용한다.
  - 처리자 이름에는 강사 목록 이름이 쓰인다(`staff_directory()`가 직원 이름에 강사 목록을 더함).

## 배포 (JIC 포털 주소 아래 /intranet)

인트라넷은 **JIC 포털(관리자 앱) Cloudflare Pages 프로젝트 안 `/intranet/`**에 올린다(11/8 결정: 포털과 같이 쓰고, 한 번 로그인으로 오간다. Cloudflare·GitHub·Supabase는 지금 쓰는 계정 하나로). 직원 화면과 가드 태블릿(출입구 공용 계정)을 같은 주소에서 쓰고, 로그인한 계정 종류로 나뉜다.

- **빌드**: Pages 프로젝트의 원래 빌드 명령 `npm run admin:build`가 관리자 앱 빌드 뒤 인트라넷을 `--base /intranet/`로 빌드해 `apps/admin/dist/intranet`에 넣는다(`apps/intranet` 의 `build:portal`). Cloudflare 빌드 설정은 바꾸지 않는다(`portal:build`는 같은 일의 다른 이름).
- **화면 주소**: `functions/intranet/[[path]].ts`가 `/intranet/…` 화면 주소에 인트라넷 `index.html`을 준다(새로 고침·바로 열기). 파일(`/intranet/assets/…`)은 그대로.
- **API**: `/intranet/api/*` = `functions/intranet/api/[[path]].ts`가 인트라넷 서버(`apps/intranet/worker/index.ts`의 `handleApi`)를 그대로 부른다. 관리자 앱의 `/api/*`(`functions/api`)와 따로 돈다. 화면은 `src/base.ts`로 주소 앞에 `/intranet`을 붙인다.
- **한 번 로그인**: 같은 주소라 관리자 앱과 같은 로그인 저장 키(Supabase 기본값)를 쓴다. 한쪽에서 로그인·로그아웃하면 다른 쪽도 같다. 관리자 앱 위쪽 **인트라넷** 버튼 → `/intranet/`, 인트라넷 **통합관리** 버튼 → `/`.
- 로컬 개발은 그대로 따로 띄운다(관리자 5173, 인트라넷 5177, 버튼은 서로의 개발 서버로). Workers 단독 배포 설정(`apps/intranet/wrangler.jsonc`)도 남아 있지만 쓰지 않는다.

- **로그인**: 이메일·비밀번호(Supabase 계정). `staff_users`에 있으면 직원, `guard_accounts`에 있으면 가드, 둘 다 아니면 안내만 보인다.
  - 직원: 관리자 앱과 같은 계정. 처리자 이름은 `staff_users.name`이고, 오른쪽 위 이름 입력 칸 대신 로그인한 이름과 로그아웃이 보인다. 가드 주소(`/guard`)는 '가드 계정으로 로그인' 안내만 보인다(직원 계정으로 외출·귀가를 기록하지 않는다).
  - 가드(출입구 공용 계정, 11/8 결정): 어느 주소로 들어와도 가드 태블릿만 보인다. 캠퍼스는 계정의 출입구로 고정되고(화면이 보낸 값은 서버가 바꿔 씀), 기록에는 근무자 이름을 고른다(설정의 근무자 목록). 가드가 부를 수 있는 API는 `/meta`, `/guard`, `/guard/scan`, `/guard/report`뿐이다(나머지 `403 guard_forbidden`).
- **학생·연수**: 업체 원본(`legacy_*`, 직원만 읽기)을 읽는다(`server/supabaseData.ts`: 메타, 학생, 연수, 기숙사 배정). 직원 요청은 직원 토큰으로(관리자 앱 `functions/api`와 같은 방식), 가드 요청은 가드가 원본을 못 읽으므로 **서비스 키**로 읽는다. 가드에게는 가드 API의 응답(재학 여부·이름·캠퍼스·외출 기록)으로만 나간다. 같은 Worker 안에서 60초 기억한다.
- **가드의 승인된 외박·카드키 비밀 값**: 가드 화면의 '외박 허용 ~복귀일'과 통금 판정에 쓰는 승인된 외박(`approvedOvernights`, 사유·담당자 메모·처리자는 읽지 않음)과 카드키 QR 서명 비밀 값(`keycard_secret`)만 서비스 키로 읽는다. 학교 여행은 가드 토큰으로 읽는다(RLS: 여행과 참가 신청(applied)만, 제외 사유는 안 보임). 외출·귀가, 가드 리포트, 패널티 후보 쓰기는 가드 토큰으로 해서 RLS가 출입구 범위를 막는다.
- **통금 위반 후보**: 가드의 귀가 기록에서는 만들지 않는다(가드 권한 밖). 직원이 홈·패널티·외출 화면을 열 때 정리하고(로컬과 같음), 화면을 아무도 열지 않아도 아래 '자동 확인'이 매시 30분에 정리한다.
- **무단결석 후보**: 직원 토큰으로 DB 함수 `intranet_absence_marks(시작, 끝)`(`20261109050000_absence_penalties.sql`, 직원만, 62일 안)를 불러 결석(학생 번호·날짜·수업 시작·캠퍼스·과목·사유 인정·마감 여부)만 받는다. 출석 표 권한은 건드리지 않았다. 가드 요청은 부르지 않는다. 함수가 없거나(강사 포털 마이그레이션 `20261109000000_attendance.sql`과 이 파일을 적용하기 전) 오류가 나면 무단결석 후보만 건너뛰고 화면은 그대로 연다(Worker 로그에 경고). 자동 확인은 서비스 키 전용 `intranet_absence_marks_service`를 쓴다.
- **저장소**: Supabase 테이블을 직원 토큰으로 읽고 쓴다(`server/supabaseStores.ts`, RLS). 계산은 로컬과 같은 core.
  - 결석·외박 승인·반려는 `decide_*` 함수, 배차·패널티 처리자는 로그인한 직원 id로 남기고, 화면에는 `staff_directory()`로 이름을 보인다.
  - 상담 기록은 테이블을 직접 못 읽으므로 `counseling.ts`의 `stores.remote`로 DB 함수(`counseling_open/create/update/followup`)를 쓴다. 목록은 `counseling_list()`(내용 없음, 맡은 캠퍼스만), 접근 기록은 DB 함수가 남긴다. 맡지 않은 캠퍼스 학생의 상담은 쓸 수 없다(`campus_not_allowed`).
  - 설정(통금·근무자)은 `intranet_settings` 한 행, 점수표는 `penalty_rules`·`penalty_stages`(종류·단계는 고정, 점수·기준만 바꿈).

### 자동 확인 (크론, 11/9 결정 I3)

- `jic-intranet` Worker(11/8 만듦)를 지우지 않고 **자동 확인 전용**으로 쓴다(`apps/intranet/wrangler.jsonc`, 코드 `apps/intranet/worker/cron.ts`). 인트라넷 화면과 `/api`는 JIC 포털 Pages의 `/intranet`이고, 이 Worker 주소로 들어오면 안내 문장만 나온다(404).
- **매시 30분**(필리핀 시각도 30분)에 통금 위반·무단결석 후보를 정리한다. 화면을 열 때와 같은 core 규칙(`scheduledChecks` → `syncPenalties`)이라 여러 번 돌려도 같은 결과이고, 통금 시각을 설정에서 바꿔도 그다음 30분에 맞춰진다. 승인·반려·설정 저장은 하지 않는다.
- 로그인한 사람이 없어 **서비스 키**로 읽고 쓴다(`serviceStores`: 처리자 비움, 외박은 승인된 것만 사유 없이). 출석은 서비스 키 전용 함수 `intranet_absence_marks_service`(`20261109180000_intranet_cron.sql`, 직원 함수와 같은 결과)로 읽는다. 직원 함수 `intranet_absence_marks`는 서비스 키에 빈 결과를 줘서 대기 중인 무단결석 후보를 지우게 되므로 쓰지 않는다. 후보 규칙은 업체 원본(학생·연수)을 읽지 않아 자동 확인도 읽지 않는다.
- Worker 변수: `SUPABASE_URL`, 비밀 변수 `SUPABASE_SERVICE_ROLE_KEY`(11/8 기록상 들어 있음). 둘 중 하나가 없으면 크론이 오류로 끝나고 아무것도 바꾸지 않는다. 결과(대기 중 통금 위반·무단결석 수)는 Cloudflare → `jic-intranet` → Logs에 남는다.
- 배포: Workers Builds가 저장소에 이어져 있어 main에 머지될 때 다시 배포되고 크론이 켜진다(11/10 #83 머지 때 `jic-intranet` 빌드 성공, Settings → Trigger Events에 `30 * * * *`). 빌드 명령 `npm run intranet:build`, 배포 명령 `npx wrangler deploy --config apps/intranet/wrangler.jsonc`. 마이그레이션 `20261109180000_intranet_cron.sql`은 11/10 적용.

   서비스 키가 아직 없으면 예전처럼 Supabase **Authentication → Users → Add user**(Auto Confirm 켜기)로 만들고 SQL Editor에서 잇는다: `insert into public.guard_accounts (user_id, campus, label) values ('<사용자 id>', 'Challenger', 'Challenger 정문') on conflict (user_id) do update set campus = excluded.campus, label = excluded.label;` 캠퍼스 이름은 관리자 앱 표시와 같게(`Challenger`, `Premium`, `MCO`).

| `trip_signups` | 참가 신청(applied)만 읽기 | 읽기, 명단 제외는 `trip_remove_signup(id, 사유)`(처리자 = 로그인한 직원, 신청 수 다시 셈). 신청·취소는 학생이 `trip_sign_up`·`trip_cancel_signup` |
| `internal_notices`, `internal_notice_reads` | - | 읽기·쓰기, 읽음은 본인 것만 |
| `counseling_notes` | - | 테이블 직접 읽기·쓰기 불가, 아래 함수만 |
| `audit_logs` | - | 관리자가 맡은 캠퍼스 기록만 읽기, 쓰기·삭제 불가(상담 함수, 학생 계정 함수 `student_account_audit`, 가드 계정 함수 `guard_account_audit` 만 남김) |

상담 기록 함수(맡은 캠퍼스만, 처리자 이름은 `staff_users.name`):
- `counseling_list()`: 목록(내용 없음)
- `counseling_open(id)`: 내용까지 돌려주고 '열람'을 남긴다(같은 직원이 10초 안에 다시 열면 한 번으로)
- `counseling_create(학생 번호, 캠퍼스, 날짜, 제목, 내용, 기한)`, `counseling_update(id, 날짜, 제목, 내용, 기한)`(기한을 바꾸면 후속 조치를 다시 연다), `counseling_followup(id, 완료 여부)`: 모두 접근 기록을 남긴다
